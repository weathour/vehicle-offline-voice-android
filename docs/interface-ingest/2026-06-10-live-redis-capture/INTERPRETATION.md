# 实车 Redis 有效样本解读记录

日期：2026-06-10

Redis：`192.168.2.112:6379`

主依据：`redis-capture-60s-1hz.jsonl`

## 1. 采集结论

- 有效完整快照：`9` 个
- 每个快照可见 key：`30` 个
- 主采集文件无读取错误
- 后续 60 次采样尝试发生超时和连接断开，仅作为追踪材料，不作为主依据

本次分析把“能读到”和“实时更新”分开处理。9 个有效样本里，底盘、电池、转向、状态类 key 有变化；定位、障碍物、车道线、红绿灯、SAM 等 payload 没变化。

## 3. 当前存在但业务数据不足的 key

### 3.1 红绿灯

来源 key：`Sensor_TrafficLightlist`

当前样本只有字段 `1` timestamp，没有 `traffic_light_num` 和 repeated `trafficlights`。因此本批样本不能提供红绿灯颜色、路口 ID、相位、剩余时间或经纬度。

### 3.2 车道线

来源 key：`Sensor_Lanelist`

当前样本只有字段 `1` timestamp，没有 `lane_num` 和 repeated `laneline`。因此本批样本不能提供车道线点列。

### 3.3 BC_Veh_Spd

来源 key：`BC_Veh_Spd`

当前样本只有字段 `1` timestamp，没有稳定速度字段。车速按 `Sensor_Location` 字段 `8` 读取。

## 4. V2X / Day2 信息

以下 key 有 payload，但需要 Day2 对应 protobuf 或 ASN.1 schema 才能做可靠语义解释：

- `Day2_BSM_Msg`：`120 bytes`
- `Day2_MAP_Msg`：`2815 bytes`
- `Day2_RSI_Msg`：`773 bytes`
- `Day2_RSM_Msg`：`249 bytes`
- `Day2_SPAT_Msg`：`962 bytes`
- `Day2_SSM_Msg`：`533 bytes`
- `Day2_VIR_Msg`：`57 bytes`

其中 `Day2_SPAT_Msg` 和 `Day2_MAP_Msg` 可能比当前空的 `Sensor_TrafficLightlist` 更有红绿灯/路口信息价值。

## 5. 与当前 App 不一致的地方

需要优先修正：

1. `Sam` 应改为或兼容 `Sensor_SAM`。
2. `Sensor_Trafficlightlist` 应改为或兼容 `Sensor_TrafficLightlist`，注意大写 `L`。
3. `DCU_INFO` 应改为或兼容 `DCU_INFO_St`。
4. 速度优先使用 `Sensor_Location` 字段 `8`。
5. `DCU_Battery_St` 字段 `4` 才是 SOC。
6. 障碍物应解析全部 repeated `obstacles`，不是只读第一个。
7. 障碍物速度要兼容字段 `9`。
8. 障碍物经纬度字段 `23/24`、尺寸字段 `12/13/14` 应进入快照模型。
9. `Sensor_Lanelist` 当前 App 没有完整读取链路。
10. 红绿灯当前样本没有业务字段，不能把空列表误报成真实“无红绿灯”。

## 6. 开发建议

短期适配顺序：

1. 更新 Redis key 名称兼容表。
2. 修正速度、SOC、续航、SAM key 的读取。
3. 扩展 `Location` 快照字段，加入 `rtkflag`、高程、pitch/roll、加速度、角速度。
4. 扩展障碍物模型，支持数量、列表、最近障碍物、经纬度、尺寸、字段 9 速度。
5. 对每个 Redis payload 记录 timestamp，并在 UI/语音输出里区分“实时数据”和“最后一次缓存数据”。
6. `Sensor_TrafficLightlist`、`Sensor_Lanelist` 在只有 timestamp 时应显示“暂无业务数据”，不要误解为检测结果为 0。
